02 / Explore the options

Three opportunities. No automatic changes.

Distinct candidate scopes add to $1,770/month in the model. Open each for evidence, a bounded test and the approval needed. One-off costs are not included.

01
Match dev compute to working hours
Non-production · lower disruption Review first
$780modeled / month

Four unreserved development VMs are modeled as running through unused evening and weekend windows. Production is outside this candidate.

Proposed next step

Validate the off-hours requirement, then pilot an agreed schedule on one development VM. Expand only after the service owner accepts the result.

Evidence to confirm

Synthetic run-state and workload calendar; confirm batch jobs, support coverage and time zone before deciding that an hour is avoidable.

Decision & safety gate

Application owner + delegated engineer. Confirm the actual approver, test window and rollback. No shutdown is authorized by this page.

How to validate the result

Compare avoided billed hours and demand-normalized cost. Confirm no missed processing, support impact or breach of the agreed service target.

Transparent model

4 VMs × $0.50 per billed hour × 390 avoidable hours per VM = $780 for a 31-day-equivalent month. All four must be validated to reach this estimate.

What is deliberately not counted in the total?

Unattached gateway · hold

A fictional $210/month candidate is excluded. The owner must distinguish an intentional dependency, a configuration defect and a genuinely unused resource before any fix-or-delete decision.

Commitments · central review

No new savings plan or reservation is modeled. First check existing shared coverage and utilization centrally. Do not add an overlapping commitment estimate to usage-reduction candidates.

Licensing & structural change

No Hybrid Benefit entitlement, region migration or redundancy change is assumed. License, network, resilience and central-platform decisions require their actual owners and additional evidence.

Data definitions, calculations & limitations

Cost & comparison

MTD modeled amortized cost is $24,360 for 1–28 October. Compare with $21,420 for 1–28 September: +$2,940 / +13.7%. Both windows have the same duration and assumed cost basis. The example is not an Azure invoice or actual negotiated pricing.

Forecast & budget

$24,360 ÷ 28 elapsed days × 31 calendar days = $26,970. Monthly budget is $30,000, leaving $3,030. This simple average assumes unchanged daily run rate; it does not model seasonality, month-end peaks or new commitments.

Unit economics

$24,360 ÷ (12,000,000 processed events ÷ 1,000) = $2.03 per 1,000 events. Prior basis: $21,420 and 10,000,000 events. The 5.2% reduction is calculated before display rounding, with the same assumed event definition.

Opportunity accounting

$780 compute scheduling + $420 storage tiering + $570 database sizing = $1,770 recurring monthly estimate on a common 31-day-equivalent basis. Candidate scopes do not overlap. Estimates exclude one-off testing/transition costs; storage includes the modeled recurring retrieval allowance.

Unknowns remain unknown

Actual approvals, performance gaps, effective entitlements, global commitment coverage, real unit prices and validated savings are not supplied. Nothing missing is shown as zero. Modeled observations are examples, not customer findings or confirmed incidents.

Scope & privacy

No live WorkIQ, billing, telemetry or Azure data is read. No external assets, calls, tracking or hidden data collection are used. Native page navigation and expandable review plans work offline; there is no submission or saved state.

04 / Choose how to proceed

A useful next step. Your decision.

Choose a path to reveal its practical checklist. These are human-review plans, not execution controls. Keeping the current configuration is a valid outcome.

PATH 01Recommended first

Prepare a dev-hours pilot

Start small, preserve production and test the $780/month candidate.

Open the review plan
  1. Confirm the real owner.Identify the accountable application owner, delegated engineer and actual approver. Verify that the selected VM is not required for off-hours work.
  2. Capture a representative baseline.Review billing, run state, processing schedule, time zone and the missing performance days. Agree service acceptance criteria before testing.
  3. Pilot one development VM.Use one agreed review window and a reversible schedule. Record the change and recovery method; expand to all four only after human acceptance.
  4. Measure before scaling.Check billed hours, processing success, support needs and normalized cost. The full $780 estimate is not a claim about the one-VM pilot.
Suggested handoff brief · select to copy

Review request — Fleet Insights: validate a reversible hours pilot on one development VM. Confirm owner, permitted hours, baseline, acceptance criteria and rollback. No production change or purchase requested.

PATH 02

Investigate before deciding

Resolve missing evidence or prepare an issue-specific guided review.

Open the evidence checklist
  • Performance & demand.Fill the two missing days and confirm peak workload, processing latency, batch schedules and demand changes.
  • Usage & dependencies.Verify access frequency for the archive set and whether the gateway is unused or incorrectly configured. Do not infer either from cost alone.
  • Commercial & control context.Check current rates, central commitment coverage, licensing entitlement and actual approvals. Include retrieval and one-off costs in a decision case.
  • Bring a focused review packet.Share only approved scoped evidence, the existing report, actions already attempted, the unresolved question and the relevant decision owners.
Suggested handoff brief · select to copy

Evidence request — Fleet Insights: complete performance coverage, verify workload dependencies and validate commercial assumptions. Review only; hold changes until the owner and actual approver accept the evidence.

PATH 03

Keep the current configuration

Document why the workload needs its current setup and set a review trigger.

Open the no-change plan
  • Record the reason.For example, required peak capacity, off-hours processing or insufficient evidence. Do not turn the estimate into an assumed obligation.
  • Keep the decision owned.Record the accountable owner, evidence reviewed and any condition that could change the decision. The page does not save this record.
  • Use an explicit review trigger.Illustrative trigger: a forecast above $28,500 (95% of budget), a changed service requirement or a significant load-pattern change.
  • Propose a review date.6 November 2026 is an example, not a scheduled meeting or agreed commitment. Use the team's normal planning process.
Suggested decision note · select to copy

No-change proposal — Fleet Insights: retain the present configuration pending a documented owner rationale. Revisit on the agreed date or trigger; no financial benefit is claimed.

Review only.Opening a path sends nothing and changes nothing. This page does not create tickets, contact owners, schedule work, buy commitments or modify Azure resources.

Design intent: one workload, a clear financial story and evidence-led choices. All values, utilization patterns, resource names, budget thresholds and proposed dates are hypothetical. Validate the facts and the actual decision rights before using this pattern with real data.
