01 / The problem

A chart is not yet a defensible decision.

Cloud-cost questions get difficult before the first graph: which resources belong, whose identity can read them, which cost view applies, and whether the numbers can be reproduced.

This repository exists to make the path from workload question to evidence to owner decision explicit and inspectable.

  • Names and ownership can be ambiguous.

    A display name is not an immutable ID. RBAC Owner describes access, not necessarily business accountability.

  • Good-looking totals can still be wrong.

    Missing pages, changed scope, mixed currencies, or different reporting periods can invalidate a comparison.

  • A confident answer is not proof.

    Agent instructions guide behavior. Deterministic helpers, independent references, permissions, and human review establish the evidence boundary.

02 / Why Zava should care

Start with one workload. Make the next conversation useful.

The intended Zava pilot is focused: approved subscriptions, existing user permissions, application-team participation, and customer-validated operating rules. Not a global autonomous rollout.

01

A shared view of the workload

Make included resources, exclusions, owner sources, dates, cost basis, and currencies visible before debating what the bill means.

02

A repeatable evidence trail

Retain the plan, raw pages, exact amounts, references, and validation status so an analyst or engineer can inspect the same reasoning inputs.

03

A practical owner handoff

Give the application team evidence it can review, then choose a guided working session, an evidence-backed remedy, or a legitimate no-change outcome.

Collect → report → owner decision → support, workshop, or no change.

These are intended workflow benefits, not measured savings or a promise to reduce Zava's bill.

03 / Under the hood

An agent for the conversation. Python for the evidence.

The current implementation is a local VS Code custom agent, five reusable skills, and standard-library Python helpers. It is not a hosted multi-user service or an OAuth on-behalf-of implementation.

04 / The people

Built for a shared conversation, not just a FinOps specialist.

Use it when the question is bounded, the invoker has authorized access, and someone can review the evidence and own the decision.

Workload and application owners

Understand which current resources are included, what they cost in the selected window, and which questions still need evidence before a change.

Primary decision makers

FinOps analysts and cloud engineers

Reproduce resource-level findings, compare appropriate native period totals, and investigate cost drivers without mistaking a hypothesis for a measured cause.

Evidence collectors and interpreters

Platform, governance, and control teams

Inspect identity, permission, scope, and lineage boundaries. Keep business accountability distinct from access rights, and keep advisory work non-enforcing.

Boundary and process reviewers

Agent and tool developers

Reuse the skill pack and Python core, extend reviewed source adapters, or evaluate another harness. Hosted use needs a separate delegated-auth and isolation design.

05 / The honest boundary

Useful to inspect. Not a blanket accuracy guarantee.

The acceptance condition is exact captured evidence under an agreed definition. A model's confidence, a passing HTTP request, or matching grand totals cannot replace it.

Reference implementation · validation in progress

Check the status before using a result.

  • BLOCKED: required inputs or complete, consistent evidence are missing.
  • UNVERIFIED: independent resource or cost references are absent.
  • Validated against captured references: bounded to the recorded comparison, not future data or final invoices.

The recorded 30 October 2026 expanded campaign exposed 11 reproducible failing cases. Offline checks and restricted model probes do not certify live Portal parity. Consult the current code and validation evidence before acceptance.

What this is not

  • A live consumption dashboard, final invoice service, or production certification.
  • A forecasting, FX, namespace/model allocation, or utilization-based rightsizing engine.
  • An autonomous cost-cutting bot that changes resources, grants roles, or creates policies.
  • A global scheduled rollout, hosted OBO service, or automatic ServiceNow integration.

Inspect the negative-first test strategy. Azure data can arrive late or be rerated; maintain the evidence window and caveats.

06 / Your first step

Bring a question. Approve a boundary.

  1. Open the repository in VS Code with Copilot agent support.
  2. Use Python 3.11+ and your own interactive Azure CLI identity, with appropriate resource/cost read access.
  3. Select FinOpsAgent. Confirm the tenant, invoker, exact subscriptions, UTC dates, cost basis, and filters.
  4. Review the resolved manifest before cost collection. Supply genuine references before claiming validation.
